A bulk corpus fetch now retries an object the store failed to serve, instead of failing the whole call on the first flake. `corpus fetch --all` asks for tens of thousands of objects at high concurrency, and `materialize` reports a per-entry failure rather than raising, so one dropped connection or throttled request ended the fetch: CI could not fetch 22 objects on one run and 6 wholly different ones on its own re-run, with the corpus itself intact, which left `main` red across three consecutive runs. `CorpusResolver.ensure` now re-asks only the entries that failed, once per `FETCH_RETRY_DELAYS` delay and at a quarter of the configured concurrency, because lowering pressure is what clears throttling. A failure that cannot be transient is not retried: an object the store does not hold, or a symlink on the path, still fails immediately with the same error and the same hint.
