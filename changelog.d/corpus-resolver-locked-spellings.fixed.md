On a case-insensitive filesystem such as APFS, another spelling of a locked corpus path (`DATA/corpus/provisions/...` for `data/corpus/provisions/...`) now names the locked file before it is fetched as well as after. `load_provisions`, `iter_provisions` and `load_source_inventory` fetch it, or refuse with fetching off, instead of reading an unfetched scope as empty. `require_materialized`, `ensure_corpus_paths`, `resolve_corpus_path`, CLI inputs and `--base` (including corpus-wide reports' whole-tree check), `corpus fetch --path` and `corpus status` treat it as the locked path. That includes the sharing and nested-checkout layouts, where a worktree's lock witnesses files in a checkout it links to: spelling the shared link `SOURCES` no longer drops that lock. Whether two spellings share a place is decided against the filesystem without writing to it: by what each reaches where the locked name exists (a directory through any link to it, a file only as itself), and below that by whether the deepest existing directory finds names in another case and the names are Unicode canonical caseless matches, which also catches spellings `fold_path` keys apart. On a case-sensitive filesystem the other spelling stays a separate path that no lock names, except that case-sensitive APFS still stores canonically equivalent names (a decomposed `é`, the Kelvin sign) in one place, and such a spelling of a file that is not there yet is taken for another path.
