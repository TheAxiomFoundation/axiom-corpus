A directory symlink at or above a protected corpus path no longer hides that path's lock. The resolver used to name a path below such a link by where the link led: outside every checkout, nowhere (a removed checkout it once shared), an unprotected directory, or another corpus path. No lock names those places, so `require_materialized` and `ensure_corpus_paths` passed over an unfetched scope, `fetch_locked_file` returned False, and `load_provisions` read an absent locked provisions file as an empty scope. Such a path now names its own protected path in the checkout holding the link, so every helper sees its lock and refuses an absent file there and names the link. A symlinked file beneath such a link is refused like one at a protected path, and `resolve_corpus_path` still brings a source file's whole directory. A directory link to the same path in another checkout (worktrees that share a corpus) is still followed, so those worktrees read and fetch that checkout's files. A file already in place beneath a directory link no longer fails `ensure_corpus_paths` because fetch will not write through the link.
