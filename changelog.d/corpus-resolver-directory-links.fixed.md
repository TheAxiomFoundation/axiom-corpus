A directory symlink at or above a protected corpus path that leads outside every checkout, to nothing (a removed checkout it once shared), or to an unprotected directory no longer hides the locks below it. The resolver used to name such paths by where the link leads, which no lock names, so `require_materialized` and `ensure_corpus_paths` passed over an unfetched scope, `fetch_locked_file` returned False, and `load_provisions` read an absent locked provisions file as an empty scope. Such a path now names its own place in the checkout holding the link, so every helper sees its lock and refuses an absent file there, naming the link, instead of reading it as empty; a symlinked file beneath such a link is refused like one at a protected path, and `resolve_corpus_path` still brings a source file's whole directory. Directory links into another checkout's protected paths (worktrees that share a corpus) still read and fetch that checkout's files, and a file already in place beneath a directory link no longer fails `ensure_corpus_paths` because fetch will not write through the link.
