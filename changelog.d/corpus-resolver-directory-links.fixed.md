A directory symlink at or above a protected corpus path no longer hides that path's lock. That includes a link at `data`, `data/corpus` or an artifact-class directory such as `data/corpus/provisions`. The resolver used to name a path through such a link by where the link led: outside every checkout, nowhere (a removed checkout it once shared), an unprotected directory, or another corpus path. No lock names those places, so `require_materialized` and `ensure_corpus_paths` passed over an unfetched scope, `fetch_locked_file` returned False, and `load_provisions` read an absent locked provisions file as an empty scope. Such a path now names the last protected path it stands at, following links inside a link's target as the operating system resolves them. So every helper sees that path's lock, refuses an absent file there, and names the link. A symlinked file beneath such a link is refused like one at a protected path, and `resolve_corpus_path` still brings a source file's whole directory. A path that reaches exactly the protected path it spells is still followed, so worktrees whose corpus directories link to another checkout's read and fetch that checkout's files. A file already in place beneath a directory link no longer fails `ensure_corpus_paths` because fetch will not write through the link. Two related gaps are also closed. A sparse checkout that holds the lock files and data without `src/` is now recognized as a checkout, so its unfetched locked files no longer read as empty. Called without `repo`, `ensure_corpus_paths` and `require_materialized` now check each path in the checkout that names it, rather than the working directory's.
