The corpus resolver no longer follows a symlinked file at a protected corpus path to its target. The link names its own path, so when a lock names that path, the `io` readers (`load_provisions`, `load_source_inventory`), `fetch_locked_file`, `resolve_corpus_path`, `require_materialized` and fetch refuse it: a dangling link no longer reads an absent locked file as an empty scope, and a link to a cache object or another corpus file is no longer taken for the locked file. Checkout spellings that `realpath` leaves apart (a case variant on APFS, the `/System/Volumes/Data` firmlink) now resolve as well, so an unfetched provisions file reached through one is fetched instead of loading as empty. A bare `data/corpus/...` path with a `..` component now resolves through the checkout like an absolute path instead of naming no locked file, and a dangling link is fetched from the checkout its target lies in, whatever the working directory. Any other live symlink is still read as before without consulting the locks.
