## Problem

Two scopes carry the Colorado Child Care Assistance Program rules (8 CCR 1403-1), and no
other scope does:

- `us-co/regulation/2026-07-13-recovery`, which the obbb, snap-fy2027 and canada-338 lines
  select;
- its successor `us-co/regulation/2026-07-13-recovery-r2026-09-11-tanf-consolidated`, which
  wave4 and wave4-r2 select.

In both, the July recovery made the retained PDF (document id `us-co-8-ccr-1403-1`) a bodyless
`document` root at `us-co/regulation/8-ccr-1403-1/3.111` over 75 `page-N` rows. axiom-encode's
resolver treats an empty body as no body and composes such a row from every descendant under its
path in the same scope (`corpus_resolver.py` at axiom-encode 7cd931de: empty bodies at 3860,
descendants by path prefix at 1140, the composition at 1314-1368). A module citing
`8-ccr-1403-1/3.111` therefore got all 75 pages, 222,420 characters, starting "Page 1 1
DEPARTMENT OF EARLY CHILDHOOD".

## Adapter change: `page_header_patterns`

Every Colorado CCR manifest drops page numbers with a `drop_line_patterns` entry such as
`^\d{1,3}$`. `_drop_pdf_line` sees only the line's text (`documents.py`, `_drop_pdf_line`), so the
pattern also drops any table cell that is a bare number. In 11042 the unsorted line stream the
adapter reads has 84 digit-only lines: 75 page numbers, the eight family sizes (1-8) of the §3.105.1
H income table on page 20, and "101201" on page 26. A copied `^\d{1,3}$` would have deleted the
family-size column.

`page_header_patterns` (new, opt-in) drops each page's running header by position. The page's k-th
line is dropped when it fully matches the k-th pattern and every line above it was dropped; the
first mismatch ends the header (`_without_page_header`). `_filtered_pdf_styled_lines` and
`_windowed_pdf_styled_lines` apply it per page before the other line filters, and `single_block`
honors it. The key is absent from every existing manifest, so no existing extraction changes.
Callers were checked by hand because GitNexus could not read its index (database version 42 vs
build version 40): `_filtered_pdf_lines`/`_filtered_pdf_styled_lines` feed only the
`single_block`, `numbered_sections` and `labeled_sections` PDF segmenters and tests.

## Extraction

`manifests/us-co-ccap-8-ccr-1403-1.yaml` runs the shared official-documents adapter with
`labeled_sections`, as `manifests/us-co-tanf-state-policy-manual.yaml` does for 9 CCR 2503-6. The
configuration differs where this PDF needs it:

| Setting | Value | Why |
| --- | --- | --- |
| `section_heading_pattern` | `3.1xx[.y[y]]` followed by an all-capitals heading | Every heading in 11042 is in capitals. The TANF pattern accepts any capitalized text, and its default heading continuation takes the next capitalized line, so the TANF rows read "3.606.1 Basic Cash Assistance A." with the "A." marker taken from the body. |
| `section_label_pattern` / `label_only_heading_pattern` | bare label, heading on the next line | 3.100-3.116 and 3.116.91-95 print the label alone. |
| `heading_continuation_pattern` | `^(?P<heading>\([A-Z][A-Z/ ]*\))$` | Only §3.116.3's heading wraps, onto "(IPV/ADH)". Nothing else continues a heading. |
| `page_header_patterns` | `CODE OF COLORADO REGULATIONS`, `8 CCR 1403-1`, `Colorado Child Care Assistance Program`, page number | Pages 2-75 open with exactly these four lines. Page 1's different header precedes 3.100, so it falls outside every section. |
| `drop_lines` | `Code of Colorado Regulations`, `Secretary of State`, `State of Colorado` | Page 1's footer, once each. Without this it lands in §3.102. |
| `drop_line_patterns` | `^_+$` | The two rules: one before 3.100, one before the editor's notes. |
| `section_label_pattern` alternative + `section_label_replacements` | `Editor’s Notes` → `editors-notes` | The amendment history becomes its own row, not the tail of §3.116.95 (the TANF rows put it in their last section). The replacement keeps the path segment in the grammar's lowercase slug form. |

`source_as_of` is 2026-07-13, the fetch date. `expression_date` is 2023-08-14, the edition's
effective date, as the TANF manifest records its rule's effective date. The replaced rows had
2026-07-13 for both. The metadata records `rule_version_id` 11042, `rule_effective_date`,
`rule_info_url` and the fetch time.

## Known limits

- **Stale edition.** The corpus holds 11042 (effective 2023-08-14). The current edition is 12658
  (effective 2026-08-14), under the renumbering described above.
- **Heading-only rows.** 3.100, 3.104, 3.110, 3.114, 3.115 and 3.116 print only a heading before
  their first subsection, so their bodies are empty. The labels are flat, so 3.104.1 is not under
  `3.104/`. For those six paths the resolver raises `CorpusDescendantStructureError` ("no
  body-bearing descendants"). For the root it raises "uncovered bodyless descendant … 3.100"
  (`corpus_resolver.py` 1328). The 9 CCR 2503-6 rows already behave the same (`3.600`, `3.600.3`,
  root). No rulespec-us module cites any of them.
- **Single-paragraph bodies.** `labeled_sections` joins a section's lines into one paragraph
  (`_normalize_text`), as for 9 CCR 2503-6. Outside `us`, the resolver slices a fragment only
  at a parenthesized marker at the start of a line (`corpus_resolver.py` 1520-1532). So a path
  such as `8-ccr-1403-1/3.111/h` cannot be sliced (`CorpusSourceSliceError`). This edition prints
  its markers as "A." and "1.", in any case.

## Follow-ups

1. **The current edition.** Carry 8 CCR 1403-1 ruleVersionId 12658, and 12277 if a line needs
   the October 2025 table, in sections with this manifest's configuration. The label patterns
   need to allow 3.1xx up to 3.124 and beyond. It then needs its own successor or scope, because
   its paths collide with this one's. Once a line carries it, re-point the rulespec-us module:
   3.111 H, and "(H)(5)(c)" in 12658.
2. **Colorado CCR tables lost to the numeric drop.** The same `^\d{1,3}$` pattern removed table
   cells from rows the consolidated scope (and so this successor) carries unchanged:
   - 61 cells of the §3.606.1 Colorado Works Standards of Assistance chart (every "Number of
     Children" label and every amount under $1,000), which rulespec-us `9-ccr-2503-6/3.606.1/F.yaml`
     encodes;
   - the 30 "Days" values of the §3.609.2 partial-month table;
   - the trailing zeros of four income bands in 1 CCR 201-2 Rule 39-22-2003
     (`2026-09-14-income-tax-regulations-r2`), which read "$88,00".

   Re-extracting them with `page_header_patterns` repairs all three.
3. **Heading-only rows in the resolver.** A bodyless row that has a heading and no descendants
   could compose to its heading instead of raising. That is a change in axiom-encode.
