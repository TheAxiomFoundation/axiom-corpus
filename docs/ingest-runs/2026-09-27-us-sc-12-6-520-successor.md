## How § 12-6-520 left the corpus

- `us-sc/statute/2026-07-13-recovery` (ed8464a37) holds three rows at the section's
  path. `us-sc/statute/12-6-520` is a `document` root with a null body. `block-1` is
  the scstatehouse.gov menu, and `block-2` is tables printed under §§ 12-6-510,
  12-6-545, 12-6-3535 and 12-6-3910. Its retained page,
  `official-documents/us-sc-code-12-6-520`, is the whole chapter 6 page
  (sha256 `ae31dbc1…`).
- `2026-07-16-pit-central-us-sc-title-12-chapter-6` (bb44b3e53) carried the section
  as extracted by the SC adapter, at jsonl line 11.
- "Deduplicate PIT release citations" (fbc9f07da) ran
  `scripts/deduplicate_release_selector.py`. When a citation is carried by exactly
  one scope of the canonical selector and one added scope, that script deletes the
  added scope's row. The canonical carrier was the recovery scope, so the real row
  was deleted and the empty root kept.
- The Act 110 successor (602cac94e) added `excluded_sections: ["12-6-520"]` to the
  `us-sc-code` entry of `manifests/state-income-tax-recovery.yaml`. Its run note
  gives the reason: the recovery scope "already supplied" the section.

Every tracked selector that selects the Act 110 scope also selects the recovery
scope. That includes the newest cut of each of the five key lines (obbb-alien-snap,
snap-fy2027-cola, canada-338, wave4, wave4-r2), so the path resolves to the menu and
the tables.

## Decision: a successor of the Act 110 scope

Two shapes were considered:

- **(a)** A successor of the Act 110 scope that restores § 12-6-520 through the
  adapter.
- **(b)** A successor of the recovery scope that holds only the adapter's
  § 12-6-520 row.

This run builds **(a)**. Only (a) lets the next cut swap cleanly while keeping the
adapter's own output. Two release checks decide it.

**The duplicate-citation check is release-wide.** `_release_citation_paths`
(`src/axiom_corpus/corpus/release_quality.py:200-252`) keys every row of every
selected scope on `citation_path` alone. When a second scope carries a path, it
reports `duplicate_release_citation` (`:239`). This applies to every selector with
the `complete-expression-dates-v1` profile, and all five key lines have it.

**The parent check is per scope.** `_validate_provision_record` looks a row's parent
up only among its own scope's rows (`:768`). The comment at `:769-770` says why:
Supabase derives versioned parent UUIDs, so a parent in another scope cannot satisfy
the foreign key.

What this means for (b):

- The adapter's § 12-6-520 row has parent `us-sc/statute/title-12/chapter-6`.
- On its own, that row fails `missing_parent_citation`.
- Adding the title and chapter rows makes them collide with the Act 110 scope.
- The adapter always writes those container rows. It has `excluded_sections`, but no
  filter that keeps only named sections (`south_carolina.py:402-495`).
- So (b) would have to ship a row the adapter does not produce: one with its parent
  cut off.

What this means for (a): the successor's paths are exactly the Act 110 scope's plus
`us-sc/statute/12-6-520`, and that path is also in the recovery scope. A cut that
drops both predecessors and adds the successor therefore carries every path it
carried before, less the recovery scope's two junk block paths, and no new
duplicate can appear. Keeping either predecessor next to the successor is a
duplicate (see [Release swap](#release-swap)).

### Act 110 does not touch § 12-6-520

The retained act, `session-laws/2026-act-110-h4216.html` (sha256 `9e3fbbd4…`), has
eight SECTIONs:

- SECTIONS 1-5 and 7 amend §§ 12-6-510(C), 12-6-50, 12-6-1140, 12-6-4910(1),
  12-6-1720(2)(a)(i) and 12-6-3632.
- SECTION 6 directs the department to adjust withholding tables.
- SECTION 8 is the effective date.

The act mentions § 12-6-520 once, inside the new § 12-6-510(C)(1), which keeps the
new brackets "indexed in accordance with Section 12-6-520". The adapter's overlay
parser agrees. `parse_south_carolina_session_law_overlay(act, section="12-6-520")`
raises "session law does not amend South Carolina section 12-6-520"
(`south_carolina.py:935`). So no overlay applies, and the restored row is the
codified text. Its history ends at 2018 Act No. 266.

## Release swap

For the next cut, drop both `us-sc/statute/2026-07-13-recovery` and
`us-sc/statute/2026-07-24-sc-act110-us-sc-title-12-chapter-6`, and add the new scope.

The newest selector of each key line selects exactly those two us-sc statute scopes.
Each check below builds the release in memory with the line's `quality_profile` and
runs `validate_release` with strict warnings. It changes no tracked selector.

| Line (newest cut) | us-sc statute, swapped | All us-sc scopes of the line, swapped | Cross-scope duplicate citations in the whole line, before → after |
| --- | --- | --- | --- |
| `us-rulespec-2026-08-08-obbb-alien-snap` | ok, 0 issues | ok, 0 issues | 0 → 0 |
| `us-rulespec-2026-09-24-snap-fy2027-cola` | ok, 0 issues | ok, 0 issues | 0 → 0 |
| `us-rulespec-2026-08-23-canada-338-suspension-union` | ok, 0 issues | ok, 0 issues | 0 → 0 |
| `us-rulespec-2026-09-14-wave4-union` | ok, 0 issues | ok, 0 issues | 0 → 0 |
| `us-rulespec-2026-09-14-wave4-r2-union` | ok, 0 issues | ok, 0 issues | 0 → 0 |

The whole-line column reads every selected scope's provisions file and counts
citation paths carried by more than one scope. That is the check behind
`duplicate_release_citation`. Deep validation of a whole line needs every selected
scope's sources, which this sparse checkout does not have (only us-sc's), so it is
left to CI's "Validate named release selectors" job on the cut that takes the swap.

Keeping either predecessor next to the successor fails:

- recovery + successor gives 1 `duplicate_release_citation` (`us-sc/statute/12-6-520`);
- Act 110 + successor gives 158.

**Scope monotonicity.** `scripts/check_release_gate.py` orders versions by
(date prefix, full string) (`_version_key`, `:35`, `:71-79`). `2026-09-27-…` sorts
after both predecessors, so the us-sc statute frontier moves forward.

A `-r2026-09-27-…` suffix on the Act 110 version would sort after it too, but the
CLI cannot produce that name. The adapter would append its title and chapter suffix
after the `-r` part, and renaming afterwards would mean re-stamping the versioned ids.
